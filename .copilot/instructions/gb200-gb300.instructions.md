# GB200/GB300 Support Project — Cross-Session Context

**Location note:** this file lives at `.copilot/instructions/` on the
fork-local **`plans`** branch of both `azhpc-images` and
`azurehpc-health-checks` (identical copy in each, alongside the existing
`plans/*.md` docs). It is **not** on `main`/upstream and not on the active
feature branches — never merge it upstream. Because it's on a branch that
usually isn't checked out, Copilot CLI won't auto-load it as a live
instructions file the way it would `$HOME/.copilot/instructions/*.md`; treat
it as a durable, git-backed reference to read at the start of a new session
(`git show plans:.copilot/instructions/gb200-gb300.instructions.md`) or check
out onto the `plans` branch to browse.

## What we're doing
Adding first-class GB200/GB300 support across two repos, plus auditing/fixing
IB & NCCL performance baselines to reflect GB300's doubled NIC bandwidth
(ConnectX-8, 800Gb/s vs ConnectX-7's 400Gb/s on H100/H200/GB200).

- `azhpc-images` — branch `michaelbeebe/gb-family-topology` (pushed to fork).
  Image customization: split `gb-family` SKU handling into `gb300-family` /
  `gb200-family`, each with its own `ndv6-gb300.sh` / `ndv6-gb200.sh`
  customization script.
- `azurehpc-health-checks` — branch `feature/gb300-v6-support` (pushed to
  fork). NHC conf + custom test baselines for `Standard_ND128isr_GB300_v6`.

See `.copilot/instructions/gb200-gb300-checklist.instructions.md` (same
branch) for the live, cross-repo checklist including dependencies between
the two repos.

## Critical confirmed facts (manager-provided, authoritative)
- **GB300 needs NO NCCL topology file.** ePCIv2 exposes PCIe topology
  natively; NCCL auto-detects it. No `NCCL_TOPO_FILE`, no `/etc/nccl.conf`
  write. This overturned the original plan (which assumed a generated
  topofile like ndv4/ndv5 had).
- **NCCL_NET_GDR_LEVEL per GPU:** A100=`SYS`; H100/H200/GB200=`PHB`.
  GB300 is **ambiguous/unresolved**: one manager note said leave it unset
  entirely for GB300 (production image default); a later, more authoritative
  perf-baseline table lists GB300 alongside H100/H200/GB200 as `PHB` — but
  that table may be describing the *test invocation* for `nccl_ib`
  specifically, not the image's system default. **Ask before setting this in
  `ndv6-gb300.sh`.**
- **SKU strings (lowercased, for vmSize case matches):**
  `standard_nd128isr_gb300_v6`, `standard_nd128isr_ndr_gb200_v6` (note the
  `_ndr_` infix is what distinguishes GB200).
- **ConnectX generations:** HBv2/HBv3=ConnectX-6 HDR (200Gb/s);
  HBv4/HX=ConnectX-7 NDR (400Gb/s); HC44=ConnectX-5 EDR (100Gb/s);
  ND A100=ConnectX-6 HDR; ND V100=ConnectX-5 EDR; ND H100/H200/MI300X=
  ConnectX-7 NDR (400Gb/s); ND GB300=ConnectX-8 (800Gb/s, rail-optimized
  1:1 NIC:GPU).
- **No public GB200/GB300 NCCL topology XML exists anywhere** — cluster-
  specific, must be generated via `NCCL_TOPO_DUMP_FILE` per-cluster if ever
  needed (moot for GB300 per the no-topofile pivot; possibly still relevant
  for GB200, unconfirmed).
- Repo `azurehpc-health-checks` has a real internal ADO pipeline
  (`dev.azure.com/hpc-platform-team/hpc-image-val`) — the GitHub repo may not
  mirror everything; check with teammates before assuming GitHub is the full
  picture.

## Authoritative IB/NCCL perf baseline table (manager-approved)
6 tests, each with A100 / H100+H200+GB200 / GB300 tiers: `uni_bw`, `bi_bw`,
`gpu_rdma_bw`, `loopback_bw`, `latency`, `nccl_ib` (single-node, forces
traffic over IB via `NCCL_SHM_DISABLE=1 NCCL_P2P_DISABLE=1`). Full details
captured in `~/ib-baselines-csv/ib-perf-baselines-recommended.csv` (local
analysis dir, not in either git repo) — treat that CSV as the canonical
reference for any baseline discussion, superseding earlier derived/guessed
comparisons (`ib-baseline-vs-theoretical.csv` has a known labeling bug and a
contested NCCL-busbw methodology — don't trust it without re-deriving).

Applied so far in `azurehpc-health-checks` (`conf/nd128isr_gb300_v6.conf`,
commit `8c9a589` on `feature/gb300-v6-support`):
- `check_ib_bw_gdr`: 380 -> 640 Gb/s (was a stale H100 copy-paste)
- Added `check_nccl_allreduce_ib_loopback 80.0 1 16G` (real IB-isolated NCCL
  test; the existing `check_nccl_allreduce` call there doesn't disable
  NCCL_SHM/P2P so it's NVLink-dominated, not IB)

`manifold_scripts` (separate, not in either repo —
`~/michaelbeebe/manifold_scripts/run_ibw_write_bw.py` and
`run_nccl_tests.py`) also has under-scaled GB300 baselines (confirmed
genuine GDR, unidirectional, matching methodology) that still need fixing in
their own repo/owner — not actionable from either of these two repos.

## Standing rules (learned the hard way this project — follow strictly)
- **Never commit/push in `azhpc-images` without an explicit ask** — the user
  has been burned by drift there before. `azurehpc-health-checks` commits
  have been fine after explicit asks, but always confirm scope first.
- **Stick to exactly what's asked.** Don't add RoCE/NVLink/other test
  variants when asked for "IB only" — this has caused visible frustration
  more than once. Don't invent SKUs, tests, or scope not requested.
- **Prefer asking for or waiting on real authoritative numbers over
  deriving/estimating them.** Several early mistakes came from guessing
  "theoretical peak" or "measured" values instead of asking. If a number's
  provenance is unclear, say so and ask rather than presenting it as fact.
  Also double check derived numbers before presenting (unit conversions,
  GDR vs non-GDR mislabeling, busbw vs raw line-rate) — these have bitten us.
- Give brief, direct answers in this project — the user favors terse,
  frustration-free responses over long explanations.
